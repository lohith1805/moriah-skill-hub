## How each fix works

Detailed rationale for every landed change — the mechanism of the bug, the approach taken, and
why that approach over the alternatives.

### C1 — OAuth2 auth-request cookie: signed JSON instead of Java serialization

**Bug.** `HttpCookieOAuth2AuthorizationRequestRepository` round-tripped the in-flight
`OAuth2AuthorizationRequest` through `org.springframework.util.SerializationUtils` —
`new ObjectInputStream(...).readObject()` on a base64 cookie value that is entirely
attacker-controlled, on the `permitAll` path `/api/v1/auth/oauth2/callback/*`, executed by
Spring Security's `OAuth2LoginAuthenticationFilter` *before* any authentication. Classic CWE-502:
a crafted payload is a guaranteed unauthenticated DoS (nested collections / hash-collision) and,
given the classpath (Spring, Jackson, Hibernate, MySQL driver, AWS SDK, POI), an RCE-class gadget
surface. No signature meant an attacker who could set the victim's cookie could also inject their
own `state`/`redirectUri` → OAuth login-CSRF.

**Fix.** The request is now serialised as a small, fixed-shape JSON DTO (`CookiePayload` —
`authorizationUri`, `clientId`, `redirectUri`, `scopes`, `state`, `additionalParameters`,
`attributes`; no polymorphic typing) via the app's `ObjectMapper`, base64url-encoded, with an
`HMAC-SHA256` tag appended: `base64(json) + "." + base64(hmac)`. The HMAC key is the existing
`moriah.jwt.secret` bytes, prefixed with a fixed domain-separation label
(`"moriah:oauth2-authz-request:v1"`) so the tag can never be replayed as, or confused with, a JWT
signature. On read: split on the last `.`, recompute the HMAC, compare with
`MessageDigest.isEqual` (constant-time); any mismatch, malformed base64, or JSON parse failure
returns `null`, which Spring surfaces as a clean `OAuth2AuthenticationException` through the
existing failure handler. There is no `ObjectInputStream` anywhere in the path.

**Alternatives rejected.** Encrypting the cookie (heavier, and integrity is what matters here, not
confidentiality — nothing secret is in it). A strict `ObjectInputFilter` allowlist (keeps the
fragile binary format; JSON is simply the right tool). PKCE was *not* added in this pass — GitHub's
OAuth app support for PKCE is historically inconsistent and it risked breaking the login flow;
noted as a follow-up.

### C2 — Multi-batch student aborts the nightly PIP run

**Bug.** `PipEvaluationService.evaluate()` loads `alreadyOpenUserIds` (users with a pre-existing
open PIP record) *once*, then loops the cohort. `currentCohortMetrics()` returns one row per
`(user_id, batch_id)`, and a student enrolled in two batches simultaneously is a legitimate,
first-class data shape (the `student_metrics` PK, the `batch_students` uniqueness, and
`MetricsRefreshJob`'s accumulator all key on the pair). So a student active in batch A *and* B who
trips a rule gets `fire()` called for the batch-A row (inserts a `pip_records` row), then the loop
reaches the batch-B row — `alreadyOpenUserIds` still doesn't contain them — and `fire()` runs
again. The second insert violates the `uq_one_open_pip` generated-column unique key on flush →
`DataIntegrityViolationException` → the whole `@Transactional evaluate()` rolls back → the job is
marked FAILED and **every PIP trigger for that night, across all batches, is lost.** It recurs
every night the student keeps tripping a rule, and leaves orphan `PIP_TRIGGERED` audit rows
(written `REQUIRES_NEW`) with no matching record.

**Fix.** One line: `alreadyOpenUserIds.add(metric.userId())` immediately after `fire(...)` inside
the loop. The set now means "users with an open record *or* already triggered this run", so the
second batch row for the same user is skipped. One PIP per user regardless of batch count is
exactly the `uq_one_open_pip` invariant, so skipping is correct behaviour, not a workaround.

### C3 — Webhook lost after the idempotency claim commits

**Bug.** `WebhookIdempotencyService.claim()` runs `REQUIRES_NEW` and commits the `webhook_events`
row (`status='RECEIVED'`, hardcoded) *before* the business handler runs. If the handler then
throws — `findById(...).orElseThrow()`, a transient deadlock, a connection drop — only the
business transaction rolls back; the claim persists. The gateway retries, `claim()` returns
`false`, and the event is never reprocessed. `processed_at` was never set anywhere and there was
no terminal-status transition, so a permanently-lost event (money captured, subscription never
activated) is byte-for-byte identical to a successfully-processed one.

**Fix — four parts.**
1. `runAndMarkProcessed(gateway, eventId, handler)` — a new `@Transactional` method that runs the
   handler (which joins the transaction via default `REQUIRED` propagation) and then
   `UPDATE webhook_events SET status='PROCESSED', processed_at=NOW(6) WHERE … status='RECEIVED'`
   in the *same* transaction. Success ⇒ business state change and the terminal status commit
   atomically.
2. `releaseClaim(gateway, eventId)` — `REQUIRES_NEW`, `DELETE … WHERE status='RECEIVED'`. The
   webhook controllers wrap `runAndMarkProcessed` in `try/catch (RuntimeException)`; on failure
   they call `releaseClaim` (so the gateway's redelivery re-claims cleanly as fresh work) and
   rethrow so the response is 5xx.
3. Stale-claim reclaim inside `claim()` — a row still `RECEIVED` and older than 15 minutes means
   the handler process was killed between the business commit and `releaseClaim`; the next
   delivery is allowed to delete and re-insert it. **Important:** this `DELETE` runs *only after*
   a confirmed duplicate-key `INSERT` failure (see the regression note in Validation) — the happy
   path is a bare `INSERT`, unchanged, so concurrent first-deliveries don't gap-lock each other.
4. `WebhookReconciliationJob` — a 10-minute `@Scheduled` sweep that logs `ERROR` for any row stuck
   in `RECEIVED` > 30 minutes, so a genuinely wedged payment is visible the next morning without
   reading gateway dashboards. It does not re-drive anything (the gateway owns redelivery).

The `WhatsAppWebhookService` (which reuses this service) was also restructured: `handleInbound`
is no longer one transaction over the whole message batch — each message is its own claim →
`runAndMarkProcessed` → release-on-failure unit, and a per-message failure is collected and
rethrown at the end so Meta redelivers only the messages that didn't complete (was I5).

### C4 — Rate limiter and audit IP collapse behind a load balancer

**Bug.** `moriah.security.trusted-proxies` is `[]` in every profile and there is no
`forward-headers-strategy`, so in the documented deployment shape (TLS terminated upstream, plain
HTTP to the app) `request.getRemoteAddr()` is the load balancer's IP for *every* request.
`RateLimitFilter` keyed on that IP, so all 10k users shared one 60-req/min bucket (≈1 req/s total
platform throughput), the per-IP `/auth/**` throttle — the only brute-force control — was
effectively disabled, and every `audit_logs.ip_address` recorded the proxy.

**Fix — three parts (a full fix still needs `TRUSTED_PROXIES` set at deploy time).**
1. `ClientIpResolver` now builds `org.springframework.security.web.util.matcher.IpAddressMatcher`
   instances from each `trusted-proxies` entry, so entries may be **CIDR ranges** (`10.0.0.0/8`),
   not just exact IPs — which is what makes a real load balancer with a dynamic egress address
   actually configurable.
2. It logs a prominent `WARN` at startup (`@PostConstruct`) when the list is empty in a non-local
   profile.
3. `RateLimitFilter` now buckets a request that carries a bearer token on
   `tok:<md5(token)>` instead of on IP, so authenticated traffic no longer collapses into one
   bucket behind a proxy regardless of `trusted-proxies`. Tokenless requests (login, 2FA, reset —
   the brute-force surface) still bucket by IP, so correct proxy config remains necessary for
   per-client login throttling; `global-requests-per-minute` was raised 60 → 300 since it is now
   a per-user budget. Account-level lockout (M12) is the complementary defence and is deferred.

### H1 — `@Async` on an unbounded executor

**Bug.** `AsyncConfig` had only `@EnableAsync`, so with `spring.threads.virtual.enabled` every
`@Async` method ran on a `SimpleAsyncTaskExecutor` whose concurrency limit is `-1` (unbounded — a
new virtual thread per task, forever, no queue, no rejection). The two real `@Async` workloads
(`InvoiceGenerationJob` PDF+S3 per payment capture, `ExportGenerationService` replica read + XLSX)
each hold DB connections while running, so a payment-webhook burst or several concurrent exports
could drain the connection pool and stall unrelated request threads with no backpressure.

**Fix.** `AsyncConfig implements AsyncConfigurer`, providing a bounded `ThreadPoolTaskExecutor`
(core 4 / max 8 / queue 100, `CallerRunsPolicy` so a saturated queue pushes work back onto the
submitter — backpressure, not unbounded growth) as the default `@Async` executor, plus a
dedicated `exportExecutor` (core 1 / max 2 / queue 10). `ExportGenerationService.generate` is
moved to `@Async("exportExecutor")` so a slow export can never starve invoice generation and vice
versa. Platform threads are correct here — these are CPU/IO-heavy batch tasks, not the
many-small-blocking-calls shape virtual threads exist for.

### H2 — XLSX exports materialise the whole result set in heap

**Bug.** Each sheet builder ran `replicaJdbcTemplate.query(sql, rowMapper)` which returns a fully
populated `List<Object[]>` *before* the first cell is written — so `SXSSFWorkbook(100)`'s
streaming only bounded the XML side, not the JDBC side. `writeAuditSheet` had no `LIMIT` on
`audit_logs` (insert-only, ~500k rows/yr), making it a multi-hundred-MB heap spike on an async
thread; concurrent exports multiply it → OOM.

**Fix.** `streamSheet(...)` creates the sheet + header first, then runs the query through a
`PreparedStatementCreator` that sets `ResultSet.TYPE_FORWARD_ONLY` +
`setFetchSize(Integer.MIN_VALUE)` (the MySQL Connector/J idiom for true row-by-row streaming) and
a `RowCallbackHandler` that writes each row straight into the `SXSSFSheet`. Only ~100 rows live on
either side at any moment. Every query is hard-capped at `MAX_EXPORT_ROWS = 200_000`; the AUDIT
export logs a `WARN` when it hits the cap (a date-range parameter is the real long-term fix, noted
in code). Cell writes also gained apostrophe-prefixing for values starting `= + - @ \t \r`
(CWE-1236 formula injection — this was L6).

### H3 — Notification dispatch is single-threaded with no HTTP timeouts

**Bug.** `NotificationWorker.drainOne()` was `@Scheduled(fixedDelay = 100)`, and a `fixedDelay`
task never overlaps itself, so there was exactly one logical consumer: throughput ≈ 1 message per
(dispatch latency + 100 ms), a few per second for the HTTP channels. A nightly PIP run enqueues
~1,500 notifications → drains over many minutes. The WhatsApp `RestClient` and the SendGrid
`Client` had no connect/read timeout, so one unresponsive provider call froze the entire
pipeline.

**Fix.**
- `drainBatch()` replaces `drainOne()`: one blocking `rightPopAndLeftPush` (so an empty queue
  still costs nothing), then non-blocking pops up to `DISPATCH_BATCH_SIZE = 8`, then the batch is
  dispatched **concurrently** on the shared bounded `applicationTaskExecutor` and the method waits
  for all of them. Redis stays a single consumer (no shared-connection blocking-command
  contention with Lettuce); only the slow per-message HTTP dispatch is parallelised. Each task is
  wrapped so one unexpected throw can't fail the whole batch `join()`.
- `NotificationClientConfig` gives the WhatsApp `RestClient` a `SimpleClientHttpRequestFactory`
  with 3 s connect / 8 s read timeouts, and builds the SendGrid `Client` with an Apache HC4
  `RequestConfig` carrying the same timeouts.

### H4 — Nightly chain has no interlock

**Bug.** The three nightly jobs (attendance finalisation 01:30 → metrics refresh 01:45 → PIP eval
02:00) are ordered only by three independent cron expressions. `@SchedulerLock` is keyed per job
*name*, so there is no interlock: if attendance finalisation runs past 01:45, metrics refresh
starts anyway and recomputes `student_metrics` against a half-finalised attendance denominator —
the exact corruption the ordering exists to prevent — and `lockAtMostFor="30m"` (double the
15-minute gap) makes the overlap plausible under load.

**Fix.** New `JobChainGuard.predecessorSucceededRecently(jobName)` — checks
`JobRunRepository.findFirstByJobNameOrderByStartedAtDesc` for a `SUCCESS` run whose `completedAt`
is within 6 hours (wider than the chain's own span, far narrower than the 24 h to last night's
run, so no calendar-date arithmetic in the scheduling zone is needed). `MetricsRefreshJob`
requires an `AttendanceFinalisationJob` success; `PipEvaluationJob` requires a `MetricsRefreshJob`
success. On a missing predecessor the job records a FAILED `job_runs` row and returns without
touching data — a diagnosable skip, not silent corruption.

### H5 — `task_submissions.verified_at` unindexed

`SubmissionVerificationRetryJob` runs `findByVerifiedAtIsNull()` every 15 minutes to find
submissions still awaiting GitHub verification; the column was unindexed so this full-scanned the
whole table 96×/day forever to return a handful of rows. **Fix:** `V17__audit_2026_08_high_indexes.sql`
adds `idx_task_submissions_verified_at` with `ALGORITHM=INPLACE, LOCK=NONE`; InnoDB indexes NULLs
(sorted first) so `IS NULL` becomes a short range scan.

### H6 — Payment captured but no subscription on a repeat payment

**Bug.** `activateSubscription` did `userSubscriptionRepository.saveAndFlush(subscription)` and
caught the `uq_one_active_subscription` `DataIntegrityViolationException` — but only *logged* it
and let execution fall through to `createPendingInvoice` + `batchAllocationService.allocate` +
`PaymentCapturedEvent`. So a user who already had an ACTIVE subscription and paid again got their
card charged, an invoice issued, possibly a batch seat — and no subscription, no auto-refund.
Worse, a caught `saveAndFlush` failure *poisons the Hibernate session*, so the outer webhook
transaction would then fail to commit with `UnexpectedRollbackException` → the payment never even
reaches `CAPTURED` → the gateway retries forever.

**Fix.** `activateSubscription` now **pre-checks** for an existing ACTIVE row
(`findByUserIdAndStatus(userId, ACTIVE)`) and returns `false` without attempting the insert — no
`saveAndFlush`, no caught constraint violation, no poisoned session. The DB constraint still
backstops the rare concurrent-double-capture race (which then fails the webhook and is retried
cleanly). `capturePayment` checks the return: on `false` it marks the payment `CAPTURED` (the
money genuinely was), writes a distinct `PAYMENT_CAPTURED_NO_SUBSCRIPTION` audit action + an
`ERROR` log for a human to action a manual refund, and **skips** invoice / allocation /
`PaymentCapturedEvent` (the last of which would otherwise try to render a PDF for an invoice row
that doesn't exist). A renewal/upgrade flow is out of scope for this pass; the conservative
"capture and flag" behaviour is safe and visible.

### H7 — `JwtAuthFilter` loads the full `User` entity per request

The filter did `userRepository.findByUuid(uuid)` — the whole entity, ~15 columns including the
`byte[]` TOTP secret — on every authenticated request, just to compare one integer
(`token_version`) and read `id`/`uuid`/`status`. **Fix:** new `AuthUserView` Spring Data
projection (`getId`, `getUuid`, `getStatus`, `getTokenVersion`) and
`userRepository.findAuthViewByUuid(uuid)`. The fresh per-request `token_version` check —
deliberate, for sub-second revocation — is unchanged in behaviour, just cheaper (four columns,
no entity hydration).

### M-batch (contained) — how each landed

- **M3 / M19 (`V18` migration).** `payments(status, captured_at)` and `leads(created_at)` back the
  `v_revenue_monthly` / `v_lead_funnel` view aggregations that were full-scanning + filesorting;
  `task_submissions(status, submitted_at)` backs `TaskSubmissionRepository.search` when `taskId`
  is null. Dropped `idx_pip_records_user` (strict left-prefix of `idx_pip_records_pull_block`,
  which also satisfies the FK) and `idx_standups_finalised` (strict left-prefix of V16's
  `idx_standups_finalisation`). All `ALGORITHM=INPLACE, LOCK=NONE`.
- **M4.** `hibernate.default_batch_fetch_size: 100` + `hibernate.order_updates: true` in
  `application.yml` — batches any lazy `@ManyToOne` touched off an entity-graph-less path instead
  of N single selects.
- **M7 (timezone).** `SubscriptionExpiryService`, `PipEvaluationService.fire`, and
  `PaymentWebhookService.activateSubscription` now compute "today" as
  `LocalDate.now(ZoneId.of(jobsZone))` where `jobsZone` is `@Value("${moriah.jobs.zone}")` — the
  exact pattern `StandupService` already uses. On a UTC host the old `LocalDate.now()` resolved to
  the previous calendar day for the late-evening-UTC / early-IST job runs, dating every PIP
  remediation window and subscription period a day short. Tests inject the field via
  `ReflectionTestUtils`, matching `StandupServiceTest`.
- **M11 (DB TLS).** JDBC URL changed from `useSSL=true` (== `sslMode=PREFERRED`, silent plaintext
  fallback, no cert check) to `sslMode=${DB_SSL_MODE:REQUIRED}` — TLS is now mandatory or the
  connection fails. `application-prod.yml` documents upgrading to `VERIFY_CA` with a pinned
  `trustCertificateKeyStoreUrl` where the DB host can be spoofed.
- **M14.** `spring.data.web.pageable.max-page-size: 100` — `@PageableDefault` only sets the
  default; Spring's built-in cap is 2000, so any list endpoint accepted `?size=2000`.
- **M15 (HTTP clients).** `GithubOAuth2UserService` builds its `RestClient` with a
  `SimpleClientHttpRequestFactory` (3 s / 8 s) instead of the timeout-less `RestClient.create()` —
  a hung `api.github.com` would otherwise pin a login thread indefinitely. `RazorpayService` moves
  `new RazorpayClient(...)` out of `createOrder` (which rebuilt the SDK's OkHttp client, pools and
  all, on every checkout) into a lazily-initialised double-checked singleton field.
- **M17 (duplicate certificates).** `CertificateService.issue` now rejects a second *live*
  certificate for the same `(user, batch, type)` via
  `existsByUserIdAndBatchIdAndCertificateTypeAndRevokedAtIsNull`. A revoked certificate does not
  block re-issue (issuing a corrected one after a revoke is legitimate), so this is a service
  pre-check rather than a DB unique constraint.
- **M20 (token reaper).** New `ExpiredTokenReaperJob` — nightly `@Scheduled` + `@SchedulerLock` +
  `JobRunTracker`, `DELETE FROM <table> WHERE expires_at < NOW(6) - INTERVAL 30 DAY LIMIT 20000`
  for `refresh_tokens` / `password_reset_tokens` / `email_verification_tokens`. Bounded per run so
  the delete never takes a large lock; a backlog clears over successive nights. 30-day grace keeps
  a just-expired token available for debugging.
- **M9 (partial).** `HrDocumentService.upload` strips `documentType` to `[^A-Za-z0-9_-]` before it
  enters the S3 key, the `hr_documents.document_type` column, and the response DTO — so it can't
  inject `/` or `..` into the key or markup into the stored/echoed value. The `ProjectService`
  asset-filename spots are bundled with the deferred M5 upload refactor.
- **M10 (partial).** New `StartupHardeningWarnings` logs a `WARN` when
  `spring.data.redis.password` is blank outside a local profile. The polymorphic-JSON cache
  serializer and a docker-compose `requirepass` were left alone — swapping the serializer risks
  breaking already-cached value shapes for little gain, and local Redis is network-isolated.
- **L2 / L17 (Hikari).** Primary pool is now fixed-size (`minimum-idle == maximum-pool-size`,
  which removes the cold-ramp TLS-handshake storm that fed the load-test p95) with explicit
  `max-lifetime` (25 m), `keepalive-time`, and `leak-detection-threshold`. `connection-timeout` is
  `${DB_CONNECTION_TIMEOUT_MS:30000}` — env-tunable for production fail-fast, default left at
  Hikari's own value (see the Validation section for why 3 s broke the concurrent ITs). The
  replica pool got the same explicit settings.

### L-batch — how each landed

- **L1.** `WhatsAppSignatureVerifier` decodes the presented hex with `HexFormat.parseHex`
  (returns `false` on non-hex) and compares digests with `MessageDigest.isEqual` on the raw
  bytes — constant-time, matching Razorpay's and Stripe's own verifiers.
- **L3.** The GitHub PR-URL regex owner/repo groups changed from `[\w.-]+` to
  `[A-Za-z0-9](?:[A-Za-z0-9._-]*[A-Za-z0-9])?` so a segment can never be `.` or `..`
  (`/repos/../../pulls/N` against `api.github.com`).
- **L9.** `Accumulator.daysSinceLastActivity` wraps the result in `Math.max(0, …)` so a
  future-dated `lastActivity` (clock skew) can't go negative and silently prevent
  `TaskAbandonedRule` from firing.
- **L10.** The invoice-number code was already correct and deliberate (`Constants.INVOICE_PREFIX`
  = `MSH-INV-<id>`, no year, explicitly contrasted with certificate numbers in its own Javadoc);
  the drift was in `architecture.md`, which was corrected.
- **L12.** Removed the `@Transactional` annotations from `NotificationWorker.markSent` /
  `recordFailedAttempt` — they are self-invoked from `processOne`, so Spring's proxy never applied
  them; each `save()` is its own transaction via Spring Data's per-call default, which is all a
  single-row status update needs.
- **L19.** `architecture.md`'s nightly-chain description updated ("several flat aggregate queries",
  the `JobChainGuard` gating). The `V10` SQL comment was **not** touched — editing an applied
  migration changes its Flyway checksum and breaks `validate` on every already-migrated database.
