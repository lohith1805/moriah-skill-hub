## Decisions Made During Build

- **2026-08-21 — Modular monolith, not microservices.** One developer, 17 days. Package boundaries are strict enough that extraction later is mechanical.
- **2026-08-21 — CodeCanyon scripts as schema reference only.** They are PHP/Laravel monoliths and cannot be extended from Spring Boot.
- **2026-08-21 — REST only, no GraphQL.** Out of scope for Phase 1–3.
- **2026-08-21 — Full 24-feature scope retained on the Sep 11 date with a single developer.** Risk accepted explicitly.
- **2026-08-21 — Features execute strictly 01 → 24; migrations numbered in the same order.** Where an early feature needs a later one, a tracked stub is used rather than reordering. This keeps Flyway versions ascending and avoids out-of-sequence migration numbers.
- **2026-08-21 — `student_metrics` is a refreshed table, not nested views.** MySQL 8 does not materialize views; stacked aggregate views would re-scan history on every PIP run.
- **2026-08-21 — Conditional uniqueness via `STORED` generated columns.** MySQL has no partial unique indexes.
- **2026-08-21 — Batch capacity via conditional atomic `UPDATE`, not optimistic locking.** A hot counter under launch-day load would thrash on retries.
- **2026-08-21 — `tier` removed from the JWT.** Entitlements are read from the DB per check so an upgrade takes effect immediately.
- **2026-08-21 — Ungraded `CODE` quiz answers excluded from the percentage denominator.** Scoring them zero would fail students on unmarked work and fire `QUIZ_FAILURE` against them.
- **2026-08-24 — Feature 01 built directly, no `/architect` session.** Single-module, no undecided design question (nothing money/auth/PIP-shaped), everything specified in `build-plan.md`. `/architect` is mandatory only for features 07, 10, 12, 17, 20 per `AGENTS.md`.
- **2026-08-24 — Testcontainers pinned to 1.20.x, not the current 2.0.x line.** Testcontainers 2.0 renamed every module artifact (`mysql` → `testcontainers-mysql`) and relocated container classes to new packages, which would break the `org.testcontainers.containers.MySQLContainer` pattern `library-docs.md` documents as this project's contract. Revisit if the context files are updated for 2.0.
- **2026-08-24 — `code-standards.md`'s approved test dependency list updated.** `org.testcontainers:junit-jupiter`, `org.springframework.boot:spring-boot-testcontainers`, `org.springframework.security:spring-security-test` added — required companions for the documented `@Testcontainers`/`@ServiceConnection` pattern to compile, missing from the original list.
- **2026-08-24 — Two DB users (`moriah_migrate`, `moriah_app`) provisioned in Feature 01, not deferred to Feature 02.** `docker/mysql-init/01-users.sql` creates both with the DDL/no-DDL grant split so the two-datasource config Feature 01 requires has something to connect to. The `audit_logs`-specific restriction on `moriah_app` is applied in Feature 02, once that table exists.
- **2026-08-24 — `IntegrationTestBase`'s MySQL container is a static-initializer singleton, not `@Testcontainers`/`@Container`.** `@Testcontainers`+`@Container` on a static field stops the container in each test class's `afterAll` and starts a fresh one (new port) for the next class, but Spring's `ApplicationContext` cache doesn't rebuild — so a second `@SpringBootTest` class silently gets a Hikari pool pointed at the first, now-dead container and every query times out ("Connection refused"). Reproduced consistently across two test classes: each passed alone, only failed combined. Fixed by starting the container once in a static initializer and never stopping it (Ryuk reaps it at JVM exit). Apply this pattern to every future integration test class.
- **2026-08-24 — Surefire/Failsafe split added so `*Test` (unit) and `*IT` (integration) classes run through the plugin `code-standards.md`'s naming table implies for each.** `SkillHubApplicationTests`/`DatabaseUserPrivilegesTest` renamed to `*IT` and `maven-failsafe-plugin` bound to `integration-test`/`verify`, so this doesn't have to be re-decided for every future controller `*IT`.
- **2026-08-24 — `permissions`/`role_permissions` seeded empty; RBAC is role-based only for all 24 features.** `V1` creates both tables so a permission-code layer can be added later without a breaking migration, but no feature reads or writes them — every `@PreAuthorize` in the build is `hasRole('X')`. Seeding invented permission codes now would be a guess against nothing that reads them. If fine-grained permissions are needed later, that's a new feature: define the actual codes a real endpoint needs, seed only those, and wire the check — not a backfill of a hypothetical catalogue. `V4`'s filename (`seed_roles_permissions.sql`) is historical and slightly misleading; kept as-is rather than renumbering every migration after it.
- **2026-08-24 — `subscription_plans.duration_days` seeded as 180 for all five tiers.** Placeholder confirmed with the user — no per-tier duration is specified anywhere in the SRS/FRS/context files. `max_projects` left `NULL` for every tier for the same reason (unspecified), and unlike `duration_days` nothing in `build-plan.md`'s 24 features reads it yet, so it wasn't worth interrupting to ask.
- **2026-08-24 — `/recover` diagnosis: three stacked bugs in the Testcontainers/`moriah_migrate` GRANT-narrowing setup, found while proving Feature 02's "moriah_app fails on UPDATE audit_logs" verify line with a real test instead of by inspection.** Each was a genuine root cause, not a guess corrected by trial and error:
  1. **`@ServiceConnection` silently ignores `spring.flyway.user`/`password`/`url`.** It contributes a `FlywayConnectionDetails` bean that Spring Boot's Flyway autoconfiguration prefers unconditionally over the properties-based one — true even when `spring.flyway.url` is also set explicitly (a `@DynamicPropertySource` setting all three together still didn't work). Fix: give the Testcontainers MySQL itself `moriah_migrate`'s credentials as its default user (`.withUsername()`/`.withPassword()`), so `@ServiceConnection` wires Flyway to the right account by construction. See `IntegrationTestBase`.
  2. **Unescaped `_` in a `GRANT ... ON db.*` database-name position is a wildcard in MySQL, not a literal underscore.** Testcontainers' `MYSQL_USER=moriah_migrate` env var makes the official image pre-create that user with its own *escaped* (`moriah\_skillhub`), literal grant before `01-users.sql` runs; an unescaped grant in that script then targets a different privilege-table row, so a later addition like `WITH GRANT OPTION` silently didn't apply to the row MySQL actually uses. Fix: escape the database name (`` `moriah\_skillhub` ``) in every `GRANT` in `docker/mysql-init/01-users.sql`, matching what the official image itself does.
  3. **MySQL privileges are additive across levels — a table-level `REVOKE` can never cancel a database-level `GRANT`.** The original design granted `moriah_app` `UPDATE, DELETE` schema-wide, then tried to `REVOKE` those two specifically on `audit_logs` in `afterMigrate.sql`. That revoke was a no-op: the schema-wide grant still applied, so `moriah_app` could update `audit_logs` the whole time — caught only because a real `UPDATE`/`DELETE` attempt was tested, not just the callback's existence. Fix: `moriah_app` gets only `SELECT, INSERT` schema-wide; `UPDATE, DELETE` are granted per-table for everything except `audit_logs` by a small stored procedure in `afterMigrate.sql` driven by `information_schema.tables`, re-run (idempotently) on every migrate so tables added by later migrations (V6 onward) are covered automatically with nobody needing to remember to update a list.

  Also fixed along the way: `afterMigrate.sql`'s `FLUSH PRIVILEGES` needed the global `RELOAD` privilege `moriah_migrate` doesn't have (and doesn't need — `GRANT`/`REVOKE` apply immediately in MySQL 8; `FLUSH PRIVILEGES` is only for direct grant-table edits) — removed.

- **2026-08-24 — Features 03 (Authentication) and 04 (RBAC and Entitlements) built together, both code-complete and `mvn verify`-green (25/25 tests).** JJWT 0.13.x HS512 access tokens (`sub`=uuid, claims `roles`/`tv`/`jti`), opaque 512-bit+SHA-256 refresh/verification/reset tokens, Redis-backed rate limiting, `EntitlementGuard`/`OwnershipGuard` for feature 04. Key decisions:
  - `TokenRevocationService` does **not** cache `token_version` in Redis despite architecture.md describing a 60s-TTL cache. `JwtAuthFilter` already loads `User` by uuid every request (required regardless, since `sub` is the uuid), so it already has the freshest `token_version` — a separate cache would be redundant and *weaker* (up to 60s of a suspended user's token staying valid). `TokenRevocationService` is used only for the JTI denylist (explicit `/logout`).
  - Accepted architecture exception: `JwtAuthFilter` (in `common/security`) imports `User`/`UserRepository` from `user/` — the architecture's own package diagram places it there while requiring a `token_version` check against `users`, with no other designated home.
  - `OwnershipGuard.canAccessKey` takes the caller's uuid (already on `AuthenticatedPrincipal`), not a userId, sidestepping the same boundary tension. Only recognizes `resumes/` and `hr-documents/` key namespaces so far; denies everything else by default until those resource-owning entities exist.
  - `EntitlementFlagsLoader` is a separate bean from `EntitlementGuard` because `@Cacheable` is proxy-based AOP — a same-class self-invocation would silently bypass the cache.
  - `EntitlementGuard` reads `user_subscriptions`/`subscription_plans` via raw `JdbcTemplate`, not a Spring Data repository, for the same "common/ can't import a future feature's entities" reasoning — the V3 tables already exist, no entity is needed for a read-only projection.
  - Logout/logout-all identify the session from the refresh token in the request body, not a validated Authorization header, consistent with `/api/v1/auth/**` being entirely public at the filter level.
  - CHAR/VARCHAR bug caught by `ddl-auto: validate`: `users.uuid` and all three `*_tokens.token_hash` columns are `CHAR(n)` in V1 SQL, but the entities used `@Column(length = n)`, which Hibernate defaults to `VARCHAR`. Fixed with explicit `columnDefinition = "CHAR(n)"` on all four columns.

- **2026-08-24 — Three real bugs found and fixed getting Features 03/04's `mvn verify` genuinely green** (not a Docker/resource issue, despite an initial "Could not start container" red herring — see below):
  1. **`SecurityConfig.filterChain()` registered its two custom filters in the wrong order.** `.addFilterBefore(rateLimitFilter, JwtAuthFilter.class)` was called *before* `.addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class)` in the same fluent chain — but `JwtAuthFilter.class` only gets a position in Spring Security's `FilterOrderRegistration` when the second call runs. Since fluent chains evaluate top-to-bottom, the first call referenced an unregistered filter class and threw `IllegalArgumentException: The Filter class ... does not have a registered order` at context startup — which cascaded into every IT class failing (`ApplicationContext failure threshold exceeded`), which in turn made the shared MySQL Testcontainer's JDBC connection attempts fail and misleadingly logged as `tc.mysql:8.0 -- Could not start container`. The container was never the problem. Fix: swap the two lines so `jwtAuthFilter`'s order is registered first.
  2. **`GlobalExceptionHandler` had no handler for Spring's `NoResourceFoundException`** (thrown by Spring Framework 6.1+ for any request matching no `@RequestMapping` and no static resource), so it fell through to the generic `Exception.class` handler and returned 500 instead of 404 for legitimately-unmapped routes. Caught by `AuthFlowIT`'s authenticated-call-to-nonexistent-route assertion. Fixed by adding a specific handler mapping it to the existing `RESOURCE_NOT_FOUND` error code.
  3. **`EntitlementGuardIT` leaked test fixture rows into `subscription_plans` across test classes.** It inserts real rows via raw `JdbcTemplate` with no cleanup, and because `IntegrationTestBase`'s MySQL container is a static singleton shared by every IT class in the same `mvn verify` run, those 2 leftover rows (5 seeded + 2 leaked = 7) broke `SeedIdempotencyIT`'s hardcoded row-count assertion when it ran later in the same suite. Fixed with `@Transactional` on `EntitlementGuardIT` (Spring's per-test-method rollback) — safe there because the guard runs in-process on the test thread; documented as **not** safe for `AuthFlowIT`, whose real HTTP calls run on a separate servlet thread with a different connection.

- **2026-08-24 — `/review` run on Features 03/04; all four findings fixed:**
  1. **Plan alignment (informational, ratified as-is):** the DB-first `token_version` check (no Redis cache) deliberately deviates from `build-plan.md`/`architecture.md`'s original "cached in Redis, 60s TTL" wording. Both documents updated to describe the direct-read design as the actual, intended behavior rather than an unimplemented spec line.
  2. **Constants & configs:** added `common/util/Constants.java` (`EMAIL_VERIFICATION_TOKEN_TTL_HOURS = 24`, `PASSWORD_RESET_TOKEN_TTL_HOURS = 1`), replacing the two magic numbers inlined in `AuthService`. Added `CacheProperties` (`@ConfigurationProperties(prefix = "moriah.cache")`) and moved `RedisConfig`'s two hardcoded `Duration` literals (entitlements 60s, default 10min) into `application.yml`'s `moriah.cache.*`, matching the `JwtProperties`/`RateLimitProperties` pattern.
  3. **IP extraction:** added `ClientIpResolver` (`common/security`) — trusts `X-Forwarded-For` only when `request.getRemoteAddr()` itself is a configured trusted proxy (`TrustedProxyProperties`, `moriah.security.trusted-proxies`, empty by default since no deployment target is chosen yet), otherwise falls back to `getRemoteAddr()`. Wired into both `RateLimitFilter` and `AuthController` (previously each called `request.getRemoteAddr()` directly, which behind any real reverse proxy/load balancer would have returned the proxy's IP for every request).
  4. **Test coverage:** added `AuthFlowIT` assertions that `LOGIN_FAILED`, `REFRESH_TOKEN_REUSE_DETECTED`, and `PASSWORD_RESET` rows actually land in `audit_logs` (previously `auditLogService.record(...)` calls existed with zero test coverage). Also added a full forgot-password → reset-password flow test (previously untested end-to-end).

  **The new reuse-detection audit-log/chain-revocation test caught a genuine, pre-existing bug, not a test-authoring mistake:** `AuthService.refresh()`'s reuse-detection branch called `refreshTokenRepository.revokeAllActiveForUser(...)` and then threw `BusinessException(INVALID_REFRESH_TOKEN)` **in the same `@Transactional` method**. The exception's default rollback silently undid the chain revocation along with it — only the `REQUIRES_NEW` audit-log row survived. In production this meant a stolen-and-reused refresh token's sibling (still-valid, rotated) token was **never actually revoked**, defeating "reuse of a consumed token revokes the whole chain" (`build-plan.md` feature 03) in exactly the scenario that guarantee exists for.   **One severe, genuine correctness bug found by `/review`'s line-by-line angle — the most consequential finding of the session so far:**
